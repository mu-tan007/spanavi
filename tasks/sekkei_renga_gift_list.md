## 決めたこと

### 1. 紐付けの鍵は `gift_shipments.lead_item_id`。向きは変えない

- 既に列がある。`gift_shipments`（送付ごと）→ `call_list_items`（企業）の**多対1**。
- 逆向き（`call_list_items` に token を持たせる）にはしない。同じ会社に2回目を送った瞬間に壊れる。
- 社名での都度突合は作らない。正規化しても16件が不一致で、TERADA のような同名別会社の実例も既にある。

### 2. 専用リストを新規に作る。既存788件リストには手を触れない

- 名前は「Renga Partners株式会社 - ギフトDM」。208件全件（リストに無い16件を含む）。
- **既存788件リストは `is_archived = true`**（最終架電 9/14）。稼働中は「製造②」(253件・最終架電 9/17)で、
  ここにギフト送付先は **0件**。二重架電の経路が無いので、`is_excluded` を立てる作業はしない。
  瀬尾・浅井に渡す母数は 788 のまま減らない。
- 過去の架電履歴（171件ぶん）は既存リスト側にそのまま残る。新リストの画面には出ない。
  履歴を新リストへ移し替えることはしない（`call_records.item_id` の付け替えは記録の改変になる）。

### 3. 🔴 リストは隠さない。「見えるが、担当者以外は架電できない」にする

**当初案（篠宮だけに見せる）は採らない。** 実データを見て変えた。

- 稼働中119リストのうち **118リストに `manager_name`（担当者）が入っている**。担当者はこの組織で
  既に全リストに行き渡った共通言語で、ギフトDMだけの特例を作る必要がない。
- 隠す設計の弱点は3つ。(a) 近い将来の解放が「配列を書き換える運用」になる
  (b) 見えないものは引き継ぎで落ちる。事故に気づけない (c) 集計との整合が崩れやすい。
- 事故の形を「**見えない**」ではなく「**押せない**」にする。見えない事故は気づけない。
- 完全な秘匿が要る案件（機微な売り手など）が将来出たら、そのときに別の壁を足す。今回は要らない。

### 4. 壁は `call_lists.caller_member_ids uuid[]`（NULL / 空 = 全員が架電できる＝今までどおり）

- **`manager_name` の上に壁を建てない。** テキストの氏名で、表記ゆれで黙って壊れる。壁は必ず member の id。
- `manager_name` は表示用のまま残す。118リストの既存運用を触らない。
- 制限をかけたいリストにだけ id を入れる。ギフトDMリストは篠宮1人。解放は配列に足すだけ。
- 止める場所は **書き込み側**。
  - `call_records` の INSERT
  - `call_list_items` の UPDATE（`call_status` の書き換え）
  - どちらも「そのリストが制限付きで、かつ自分が担当でない」なら弾く。
- **SELECT は誰も絞らない。** ランキング・報酬・事業俯瞰・アポの合計は1ミリも動かない。
- 画面は、担当者でない人には発信ボタンを出さず「担当：篠宮 拓武」と出す。

### 5. dorayaki AI タブは施策単位に一般化する。架電結果タブにも出す

- **両方に出す。** 役割が違う。
  - 架電結果タブ＝リスト別の架電量と結果。ここからギフト分を抜くと、クライアントが見る
    「今月の架電数」が実態と合わなくなる
  - dorayaki AI タブ＝施策の導線（送付 → 到着 → 読み取り → 押された導線 → 架電 → アポ）
- **タブ名を施策中立にする。** 次回はどら焼きが入らず手紙だけ。「dorayaki AI」は名前負けする。
  `gift_shipments.campaign` は既にあり、今は `renga_20260918` の1本。
  施策が増えたらキャンペーンの切替を1つ置く。**表は施策ごと、タブは1枚。**
- 施策と架電リストの対応に新しい列は要らない。`lead_item_id → call_list_items.list_id` で辿れる。
- ビューに `lead_item_id` から引いた **最新の架電ステータス・架電日時・録音URL** を足す。
- 画面で数えない（集計はビュー1本、という既存の決めを守る）。
- 録音は `call_records.recording_url` に既に残る仕組みがある。新しく作るものは無い。

### 6. 到着日は小澤様を待たずに埋める

- 送り状番号208件とキャリアが揃っている。ヤマト・佐川の追跡から配達日を取って `delivered_on` に入れる。
- 小澤様からデータが来たら突き合わせる。

## やらないこと

- 読み取り（SELECT）に壁をかけない。ランキング・報酬・事業俯瞰・アポの数字を動かさない
- `manager_name`（テキストの氏名）の上に壁を建てない
- 118リストの担当者運用を新しい仕組みへ移し替えない
- フロントだけで止める（APIを叩けば書ける。壁と呼べない）
- 既存の架電記録を新リストへ移し替える
- 既存788件リスト（アーカイブ済み）を触る
- 16件の素性調査（先方の選定。リストに足すだけ）
- `gift_shipments` の主キー（`token`）を触る

## 答え合わせ（実装後にこれを測れば正しいと言える）

1. 篠宮以外のアカウントで、このリストの企業に架電記録を書こうとして **弾かれる**こと
2. 同じアカウントで、このリストが**一覧には見え**、発信ボタンが出ず担当者名が出ること
3. 他のリストでは、誰でも今までどおり架電記録を書けること（118リストの運用を壊していない）
4. **壁の前後でランキング・報酬・事業俯瞰の合計が1件も変わらないこと**
5. Renga様のポータルで208行と架電ステータス・録音が見えること（実画面で確認）
6. `gift_shipments` 208件すべてに `lead_item_id` が入ること

## 実装の順番

1. `call_lists.caller_member_ids` を追加し、`call_records` INSERT と `call_list_items` UPDATE の
   ポリシーに条件を足す（低負荷時・`lock_timeout` を先に設定）
2. 専用リストを作り、208件を投入。`lead_item_id` を埋め、`caller_member_ids` に篠宮を入れる
3. `gift_shipment_stats` を広げ、GiftDmTab に「架電ステータス／結果／録音」の列を足す
4. タブ名を施策中立にし、キャンペーンの切替を置く
5. 到着日を追跡から埋める
6. 答え合わせ1〜6

**1と2の順序は入れ替えない。** 壁の無い状態で208件を入れると、その間だけ誰でも架電できる。
