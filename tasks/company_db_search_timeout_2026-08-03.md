# 企業DB検索の statement timeout（2026-08-03）

## 症状

企業DBで下記の条件で検索すると `エラー: canceling statement due to statement timeout`。

都道府県=東京都/神奈川県/愛知県/大阪府 ／ 株主タイプ=個人のみ ／ 代表・株主一致 ／
企業DBラベル=M&Aニーズあり ／ 売上高 300,000千円以上（空欄含まない）／
当期純利益 20,000千円以上（空欄含まない）／ 代表者年齢 65以上（空欄含まない）

authenticated ロールの `statement_timeout` は **8秒**。実測 **17.9秒** で打ち切られていた。
条件自体は正しく、本来 **134社** がヒットする。

## 原因

`company_master_rep_in_shareholders_financial_idx` は `(net_income_k, revenue_k)` の2列しか持たない
部分索引だった。btree なので範囲条件で効くのは先頭列だけ、つまり
「当期純利益が閾値以上」の **43,168件** が索引から出てくる。
都道府県・代表者年齢・株主タイプはその43,168件について本体テーブルを1行ずつ読んで判定していた。

- ランダム読み1回 ≒ 0.33ms（＝このインスタンスのIOPS上限）× 43,168回 ≒ 16秒
- 株主タイプの `classify_shareholder_type()` は行ごとに実行されていたが、
  **CPU時間ではなくディスク読み込みが支配的**（関数を列に置き換えても16.7秒のままだった）
- さらにプランナはこの索引で「3行しか出ない」と見積もっており（実際43,168件）、
  他の索引に切り替わることもなかった

## 対処（本番適用済み）

1. `company_master.shareholder_type` 列を追加（`20260803190000`）
   - `classify_shareholder_type(shareholders)` の算出結果を保持。索引に載せられるようにするのが目的
   - 既存トリガ `trg_normalize_company` で維持（shareholders が変わったときだけ再計算）
   - 49万行を id レンジで5万〜12万行ずつバックフィル。8,985行の抜き取り検査で不一致0件
   - `idx_cm_shareholder_type` を追加。株主タイプ単独の件数取得は index only scan で13ms
2. RPC `search_company_master` を新列参照に変更（`20260803190100`）
3. **被覆索引に入れ替え（`20260803190200`）＝本命**
   - `company_master_rep_in_shareholders_cover_idx`
     `(net_income_k, revenue_k, prefecture, city, industry_major, industry_sub,
       representative_age, shareholder_type, employee_count, established_year, id)`
     partial: 代表者名が株主欄に含まれる行のみ（259,545件・36MB）
   - 旧 `_financial_idx` / `_id_idx` は撤去。**残すとプランナが「安く見える」旧索引を選び続ける**
   - index only scan は可視性マップ依存なので、バックフィル後に `VACUUM (ANALYZE)` 実施

## 結果（実測）

| 検索条件 | 前 | 後 |
|---|---|---|
| 報告された条件（ラベル込み） | 17,977ms | **94ms** |
| 同（RPC全体・並べ替えあり） | タイムアウト | **92〜138ms** |
| 大分類＋代表株主一致＋売上 | 12,297ms | **226ms** |
| 代表・株主一致のみ | — | 150ms |
| 都道府県＋市区町村＋代表株主一致＋従業員 | — | 142ms |
| 株主タイプ単独 | タイムアウト懸念 | 13〜36ms |

## 残っている課題（今回の不具合とは別・以前から）

代表・株主一致を使わない検索は上の部分索引が効かないため、本体テーブルの読み込みが残る。

- キーワード検索「介護」: 7.3〜11.7秒（**8秒を超えることがある**）
  - 原因は別。2文字の日本語は trgm のトライグラムが少なく、GIN が大量の偽陽性を返して
    本体テーブルの再検査が膨らむ。pg_bigm 等の別方式の検討が要る
- 電話番号前方一致「03」: 3.9〜6.1秒
- 都道府県＋売上＋従業員（代表株主一致なし）: 2.8〜5.3秒

いずれも「代表・株主一致を含まない条件用の被覆索引」を1本足せば同じ理屈で解消できる見込み
（非部分索引で約50MB）。ただし索引が増えると取込時の書き込みが重くなるので、
リスト取込の頻度と見合いで判断したい。

## 前提メモ

- インスタンスの `shared_buffers` は 256MB、company_master は本体514MB＋索引800MB。
  キャッシュに乗り切らないので、ランダム読みの回数がそのまま応答時間になる
- MVリフレッシュ cron が15分ごと（:11 :26 :41 :56）に走っており、
  その間は `DROP INDEX` が AccessShare で待たされる。索引の入れ替えは
  「新索引を別名で作成 → 旧索引 drop → rename」の順で無停止に行うこと
