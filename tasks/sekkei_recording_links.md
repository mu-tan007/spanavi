# 録音が「社内でも、クライアントに渡したリンクでも」滞りなく聞ける状態にする

設計担当: Fable 5.1 / 2026-09-04
きっかけ: レバレジーズM&Aアドバイザリー 山村様より「以前のアポ4件が携帯で聞けない」（2026-09-04）

---

## 論点

録音の置き場を Supabase Storage から Cloudflare R2 へ移した（2026-08-23〜24）結果、
**外へ配ったリンクだけが死んだ**。同じことを二度起こさないための、リンクの持ち方を決める。

### 6. 社内の再生経路は既に一本化されている

### 7. クライアントが録音に触れる経路は1つしかない

`src/components/client/` に録音再生は無い。
**クライアントポータルでは録音を聴けない。** 先方が録音に辿り着く唯一の道が、
Slackに貼られた rec リンク。ここが切れると代替手段がゼロになる。

### 8. 外へ配ったリンクの寿命が、R2の資格情報に縛られている

`recordingSource.ts` の `shareSecret()`:

```
Deno.env.get('REC_SHARE_SECRET') ?? Deno.env.get('R2_SECRET_ACCESS_KEY')
```

**【2026-09-04 追記・訂正】** `supabase secrets list` で確認したところ、
`REC_SHARE_SECRET` は **2026-08-25 09:23 に独立した値で設定済み**だった
（ダイジェストが `R2_SECRET_ACCESS_KEY` と異なる）。
したがって「R2のキーを入れ替えると配布済みリンクが死ぬ」危険は**実際には無い**。
ただしフォールバックが残っていると、将来この値を消したときに黙って再結合するので、
`?? Deno.env.get('R2_SECRET_ACCESS_KEY')` は外した（実装済み）。

## 決めたこと

### A. 外へ出すリンクは「我々が握る不変の入口」に固定する（今の rec 形式を正式に採用）

- 外部へ渡す録音URLは `/functions/v1/rec/<鍵>?s=<署名>` 以外を使わない。
- この形の要件は3つ。**期限を持たない・鍵が変わらない・転送先を我々が差し替えられる。**
- 置き場所（R2 / 別クラウド / 将来の移設先）が変わっても、このURLは変えない。
  移設のたびに rec の中の転送先だけを直す。
- **理由**: 報告文はシステムの外（Slack・メール・先方の手控え）へ手でコピーされる。
  一度出た文字列は二度と直せない。だから外に出す文字列は永久に有効でなければならない。

### B. 署名の素を R2 の資格情報から切り離す（設定済みだった。フォールバックのみ撤去）

- `REC_SHARE_SECRET` を独立した値として設定し、`?? R2_SECRET_ACCESS_KEY` のフォールバックを消す。
- 設定が無いときは**空URLを返して呼び出し側に旧来の値を使わせるのではなく、保存を失敗させる**。
  黙って旧形式に落ちると、また「外だけ死ぬ」が再発する。
- **2026-09-04 実測: `REC_SHARE_SECRET` は 8/25 に設定済み。** 危険は空振りだった。
  フォールバックだけ撤去し、既存445本の署名が変わらないことをデプロイ後に実測で確認済み。
- **やり直しが効かない判断**: いま設定する値が、今後配る全リンクの寿命そのものになる。
  この値は「一括失効させたい時にだけ変えるもの」として台帳に記録する
  （[[reference_anthropic_api_keys]] と同じ扱い）。

### C. 保存期間は「消さない」で確定（むー様承認 2026-09-04）。180日の記述は消す

- **根拠**: 録音は成果物の証跡。M&Aソーシングは面談→成約まで年単位で動く。
  436件のうち最古は6か月前で、今まさに参照されている。
  180日で消すと「アポ報告に貼ったリンクが半年後に必ず死ぬ」設計になり、Aと矛盾する。
- 容量は R2 なので Supabase の100GB上限とは無関係。80GB/15万件を持ち続けても費用は月数ドル規模。
  **消す理由が費用でないなら、消さない。**
- 対外文言3か所（`rec/index.ts:103`・`SessionVideoModal.jsx:36`・`videoUpload.ts:89`）から
  180日の記述を削る。契約・利用規約に保存期間を書いているなら、そちらも合わせる。
- **2026-09-04 むー様承認済み。消さないで確定。** 実装済み（対外文言3か所から180日を削除）。

### D. 410 の文言を、理由ごとに分ける

- 期限を設けない（C）なら、「保存期間が過ぎています」は**必ず嘘になる**ので消す。
- R2に無いときは「録音が見つかりません／担当者までお問い合わせください」に統一する。
- 同時に、Supabase Storage へのフォールバックを3ファイルから削る（バケットが無い＝到達不能）。
  残しておくと、次に読む人が「まだ2か所を見ている」と誤解する。

### E. 過去436件は、Slackへ貼り直す（むー様承認 2026-09-04・全37社へ実施）

- 旧URLのドメインは `baiiznjzvzhxwwqzsozn.supabase.co` で、
  `/storage/v1/...` の経路は Supabase の持ち物。**我々が転送を差し込めない。**
  バケットを作り直して80GBを戻すのは、移設した理由（100GB上限）を自分で壊す。
- したがって**旧URLの復活は不可能**。37社のチャンネルへ新URLを貼り直す。
- 一覧は機械的に作る（クライアント別・報告日順・企業名と新URL）。
  文面は1社1通にまとめ、報告ごとに分けない（37通で済む。436通は先方の迷惑）。

### F. 再発防止の本体は「報告の投稿をシステムから行う」

- 今はDBの `appo_report` を人が手でコピーしてSlackへ貼っている。
  だから**システムが後から直せない**。これが今回の被害を生んだ構造そのもの。
- アポ報告のSlack投稿をシステム経由にすれば、URLが変わっても `chat.update` で直せる。
- ただし**これはA〜Eより後**。A・Bが入っていればURLはもう変わらないので、Fは保険。
  先に作ると、直す必要のないものを直せる仕組みを作ることになる。

## 【重大な訂正】180日の削除規則は**生きていた**（2026-09-04）

`lifecycle-get` が403で読めなかったことを「規則が入っていない」と読んだのは**誤り**だった。
403はAPIトークンにライフサイクル**読み取り**権限が無いだけで、規則の有無とは関係がない。

実体をGETしたときの応答ヘッダに、規則がそのまま出ていた。

```
x-amz-expiration: expiry-date="Fri, 19 Feb 2027 14:13:20 GMT", rule-id="delete-recordings-180d"
```

| 対象 | 消える日 |
|---|---|
| 移設で運んだぶん（8/23〜24にR2へPUT） | **2027-02-19〜20** に一斉 |
| 移設後に新規保存されたぶん（例: 9/3収録） | PUTから180日後（例: 2027-03-02） |

**規則の起点はR2に置いた日**なので、3月に録った通話も8月に録った通話も同じ日にまとめて消える。

### いま何が食い違っているか

むー様は「消さない」で確定された。それを受けて対外文言から180日の記述を削除済み。
しかし**R2側の規則は残っている**。このままだと、
**何も告知しないまま2027年2月19日に15万件が消える**。文言を消したぶん、かえって危ない。

### 直すには

現在のR2 APIトークンは lifecycle の読み書きができない（`lifecycle-get` / `lifecycle-set` とも403）。
どちらかが要る。

1. **Cloudflareのダッシュボードで `delete-recordings-180d` 規則を削除する**（最短）
2. R2 APIトークンにライフサイクル権限を足し、こちらから削除する
   （`r2` Edge Function には `lifecycle-set` はあるが**規則を消す口が無い**ので追加が要る）

### 答え合わせ

規則を消したあと、実体をGETして **`x-amz-expiration` ヘッダが返らないこと**を確認する。
`lifecycle-get` が200になるかどうかは、トークン権限次第なので判定に使わない。

⚠️ **教訓**: 保存期間が入っているかは `lifecycle-get` ではなく、
**実体のGET応答の `x-amz-expiration`** で見る。前者は権限で黙って403になる。

### むー様のご判断が要る点（更新）

規則を削除するまでの間、対外文言の180日の記述は**戻したほうがよい**か。
（消えるのは2027年2月なので当面の実害はない。規則をすぐ消すなら戻す必要はない）
